# Ebrahimi Inventory — Project Context

Last reviewed against the repository: 2026-10-26.
Purpose: a project map for AI assistants and developers. All file paths below are
relative to the repository root. This document describes the current code, not a
guarantee that every feature has been tested or completed. When code changes,
update the relevant section; current source files take precedence over this map.

## 1. Project overview

Ebrahimi Inventory is a web application being developed for the owner's father's
shop. It manages product categories, products, purchase and selling prices,
inventory receipts, sales returns, buyers, and sales invoices.

- Audience: shop staff managing everyday inventory and sales.
- Application language: Persian (Farsi), with a right-to-left layout.
- Product and receipt prices remain integer toman amounts. New invoices use
  integer rial amounts, explicitly convert product prices by 10, and persist
  currency = IRR. Legacy invoices/movements retain currency = TOMAN. Invoice
  previews convert legacy amounts to rial once; movement views convert IRR
  prices to toman for consistency with inventory screens.
- Quantities and stock are integers; fractional stock is not currently modeled.
- Architecture: Vue SPA -> NestJS JSON REST API -> Prisma -> PostgreSQL.
- Status: active development. The redesigned UI includes a dashboard using the
  existing product/movement APIs. Reports remain a placeholder; the frontend
  uses local components and Reka rather than a complete shadcn-vue scaffold.

## 3. Repository layout and technology

- package.json / package-lock.json: root dependencies, including Prisma 7,
  PostgreSQL adapter/driver, and several NestJS support packages. There are no
  root application scripts or npm workspace orchestration.
- Backend/: NestJS 12 and TypeScript REST API; its own package.json and lockfile.
- Frontend/: Vue 3, TypeScript, Vite 8, Vue Router, and Pinia; its own package.json
  and lockfile. The @ alias resolves to Frontend/src/.
- prisma/schema.prisma: PostgreSQL schema and generated-client destination.
- prisma/migrations/: database migration history.
- prisma7.config.ts: Prisma CLI configuration, schema path, migrations path,
  and DATABASE_URL loading.
- Backend/src/generated/prisma/: configured Prisma client output, imported by
  the API. Regenerate it from the schema rather than hand-editing it. Do not
  confuse this with any separate root-level generated/ directory.
- context/aboutProject.txt: this project overview.
- Postman/: supplementary API materials; controllers and DTOs are authoritative.

Frontend UI dependencies include Reka UI, @lucide/vue, class-variance-authority,
clsx, tailwind-merge, ECharts, and vue-echarts. Exact dependency versions and
available scripts belong in each package.json and lockfile.

Backend uses ES modules and NodeNext resolution; existing local TypeScript
imports use .js extensions. PrismaService extends the generated PrismaClient,
uses PrismaPg, and connects/disconnects through Nest lifecycle hooks.

Pinia is registered, but src/stores/counter.ts is a starter example. Most business
state currently lives in Vue views through refs/reactive objects and API calls.

## 5. UI direction, theme, and migration status

The requested direction is to remove Element Plus and move to shadcn-vue.
Element Plus is absent from the current frontend package manifest and source
usage. However, the current UI is a mixture of local components, native HTML
controls, custom CSS, and Reka primitives. It is not a fully scaffolded
shadcn-vue/Tailwind component system. tailwind-merge alone does not provide
Tailwind CSS; the current frontend manifest has no Tailwind CSS dependency.

- Preserve Persian labels, RTL behavior, and the bundled Vazirmatn font.
- Global styles and semantic color tokens live in src/styles/main.css.
- :root defines light colors; :root.dark defines dark colors.
- Theme state is stored in localStorage under "theme", with "light"/"dark" values.
- src/main.ts applies the saved theme to document.documentElement before mount.
- App.vue provides navigation, a Reka mobile drawer, and a Reka low-stock popover.
- composables/useTheme.ts initializes the saved theme, falling back to the system
  preference on first visit, and exposes the shared theme toggle. Storage failure
  does not prevent the application from rendering or toggling themes.
- Use existing tokens such as --background, --foreground, --card, --primary,
  --muted, --border, and --destructive when extending styles. Chart text, grid,
  and tooltips follow the current theme. Keep both themes visually checked.
- Invoice printing has dedicated styles in components/InvoicePaper.vue and main.css.
  Preserve a readable printed invoice when changing screen layouts or themes.

Continue the requested migration without reintroducing Element Plus. Inspect
the existing local component API before assuming a standard shadcn-vue API.

## 6. Data model

Source of truth: prisma/schema.prisma. IDs are auto-incrementing integers except
StoreSettings, which is used as a single record with id = 1.

| Model | Meaning and key constraints |
| --- | --- |
| Category | Unique name; one category has many products |
| Product | Unique SKU, required category, name/unit, integer buyPrice/sellPrice, stock/minStock, optional description, isActive |
| PriceHistory | Per-product old/new buy and sell prices, SINGLE/BULK type, optional change percentage and actor metadata |
| AuditLog | Per-product action and optional JSON details; selected operations are logged |
| InventoryTransaction | Product movement, type, positive quantity for implemented flows, optional unit price, description, and invoice relation |
| Buyer | First/last name, optional unique nationalId, phone, address, notes |
| Invoice | Short unique number, issue date, buyer/seller snapshots, currency, subtotal/discount/paidAmount/total, settlement, notes, items, and movements |
| InvoiceItem | Product reference plus name/unit snapshots, quantity, unitPrice, and total |
| StoreSettings | Store name, address, phone, optional logoUrl, iban, and defaultInvoiceNotes |

Product-related history, audit logs, movements, and invoice items use restrictive
foreign keys. Deleting a category with products is also restricted. Deleting a
buyer sets Invoice.customerId to null; invoice buyer snapshots remain intact.

PriceHistory.changedById/changedByName do not imply an implemented user system.
There is no User model in the current schema.

## 7. Business rules and workflows

Products and prices — Backend/src/products/products.service.ts:

- Product creation requires an existing category. Initial stock defaults to zero;
  product create/update DTOs do not expose stock editing.
- Low stock means stock <= minStock.
- Price changes through product editing or price endpoints record price history
  and an audit entry in a database transaction.
- Bulk price changes target active products, optionally within a category, and
  operate on either BUY or SELL prices. Preview does not write data.
- PERCENTAGE computes round(oldPrice * (1 + value / 100)). FIXED sets the price
  to round(value); it is not an increment. The redesigned UI labels this as
  replacing the current price and invalidates the preview when inputs change.
- Deleting a product with price history deactivates it. Otherwise the service
  attempts physical deletion, which other restrictive relations may reject.

Inventory — Backend/src/inventory/inventory.service.ts:

- PURCHASE and RETURN both increase stock and create movement records.
- RETURN requires an invoice and cannot exceed the sold quantity for that
  product on that invoice minus quantities already returned.
- An optional unitPrice on receipt updates buyPrice; a changed buyPrice also
  creates price history. Receipt operations create a STOCK_RECEIVED audit entry.
- ADJUSTMENT exists in the enum and movement DTO but is rejected by the service.
- SALE movements are created by invoice issuance, not by the receipt endpoint.
- Movement quantities are stored as positive values; the movement type determines
  whether the operation adds to or removes stock.

Invoices and buyers — the same inventory service and InvoicesView.vue:

- The frontend builds an in-memory draft, selects a saved buyer, then posts items.
  Drafts are not persisted as database records or browser storage. An in-app
  route-leave dialog warns before discarding a draft; full browser reloads do
  not persist it.
- The UI requires a buyer. The API also supports optional customerId and buyer
  snapshot fields; its contract is broader than the current UI.
- Invoice creation requires at least one item, active products, positive integer
  quantities, and nonnegative integer unit prices. The supplied line price is
  used; it does not have to match the product's current sellPrice.
- In one database transaction, the API saves the invoice and item snapshots,
  conditionally decrements stock, and creates SALE movements. Insufficient stock
  causes rollback rather than a partially saved invoice.
- Item total = quantity * unitPrice; subtotal = sum of item totals;
  total = subtotal - fixed discount. paidAmount must be between zero and total.
  CASH/INSTALLMENT records settlement choice; this is not a payment ledger.
- Invoice numbers use the database ID padded to at least three digits. Existing
  numbers were converted by the invoice-editor migration; IDs and relations stay intact.
- issueDate is independent of createdAt. The editor defaults to today in Tehran
  and displays a Persian calendar; the API accepts an ISO YYYY-MM-DD date.
- PATCH /invoices/:id replaces lines and SALE movements and reconciles stock
  in one Serializable transaction. Invoices with returns cannot be edited.
- Editor lines scroll in one table. Only preview/print paginate (ten items per
  A5 landscape sheet). Header/logo/number/date/page repeat; parties only appear
  on the first sheet and totals/notes/settlement/IBAN/signatures on the last.
- New invoices snapshot store details and the selected buyer. Store default
  notes prefill the draft and can be overridden per invoice (600 characters).
- Archive filters support buyer/customer, product name/SKU, and date range.
  Date filters use the persisted issueDate (a date-only field).
- Successful issuance shows the saved invoice with an explicit print action.
  Draft previews are marked as unregistered and do not change stock. The print
  action is explicit and waits for fonts, images and page fitting. Existing
  invoices can be reopened, edited when eligible, and printed. No server PDF endpoint.
- Returns restore stock and record movements; they do not revise the original
  invoice total or create a financial refund record.
- Store settings are persisted through the API, using record id = 1.

## 8. API surface and contracts

Default API base: http://localhost:3000/api/v1.
All endpoint paths below are relative to /api/v1.

| Resource | Endpoints |
| --- | --- |
| Categories | GET/POST /categories; GET/PATCH/DELETE /categories/:id; GET /categories/:id/products |
| Products | GET/POST /products; GET/PATCH/DELETE /products/:id |
| Product status | PATCH /products/:id/status |
| Product prices | PATCH /products/:id/price and /products/:id/prices (aliases) |
| Price history | GET /products/:id/price-history |
| Bulk prices | POST /products/bulk-price-update/preview; POST /products/bulk-price-update |
| Inventory movements | GET/POST /transactions |
| Buyers | GET/POST /buyers; GET/PATCH/DELETE /buyers/:id |
| Invoices | GET/POST /invoices; GET/PATCH /invoices/:id |
| Store settings | GET/PUT /store-settings |

Controllers define routes, DTOs define accepted payloads, and services enforce
business rules. Backend/src/main.ts enables a global ValidationPipe with
transform, whitelist, and forbidNonWhitelisted; unexpected payload fields are
rejected. Frontend service wrappers live in src/services/{api,categories,
products,inventory}.ts and use fetch, not Axios.

Products and price history return { data, meta }, with page, limit, total, and
totalPages in meta. Other list endpoints generally return arrays. Product list
queries support search, categoryId, isActive, lowStock, minPrice, maxPrice,
sortBy, sortOrder, page, and limit. Read DTOs for defaults and allowed values.

Current pagination limits matter: product listing loads matching rows before
filtering/slicing in memory; ProductsView requests up to 10,000 products and
also paginates locally. Transactions and invoices return at most the newest
500 matching records, without a pagination response. Do not treat these as
complete exports or scalable server-side pagination.

No authentication module, authorization guards, login flow, or Swagger setup
is wired into the current application. JWT/Passport/Swagger dependencies and
JWT variables in .env.example are not evidence of those features being active.

## 9. Local configuration and development commands

Use each command from its stated directory. The frontend declares Node
^22.18.0 || >=24.12.0; check package.json if the runtime requirement changes.

Configuration:

- Root .env.example lists PORT, DATABASE_URL, JWT_SECRET, and JWT_EXPIRES_IN.
  Create/configure the local root .env without copying credentials into docs.
- Backend/src/app.module.ts loads ../.env relative to the backend working
  directory. PrismaService requires DATABASE_URL; default API PORT is 3000.
- Frontend VITE_API_URL overrides the default http://localhost:3000/api/v1.
- Backend CORS currently allows http://localhost:5173 only. Coordinate API URL,
  port, and CORS changes when using another frontend origin.
- PostgreSQL must be available separately; docker-compose.yml does not currently
  define a usable database service.

Dependency installation: run npm ci in the repository root, Backend/, and
Frontend/ as separate packages. Consult their manifests/lockfiles if dependency
resolution fails; these are not a single npm workspace install.

Database preparation, from the repository root:

    npx prisma generate --config prisma7.config.ts
    npx prisma migrate deploy --config prisma7.config.ts

The explicit --config matters because the config is named prisma7.config.ts.
The migration command applies existing migrations to DATABASE_URL; point it at
the intended development database. For schema changes, use the project's
versioned migration workflow and regenerate the client; do not hand-edit output.

Backend/, in its own terminal:

    npm run start:dev

Frontend/, in another terminal:

    npm run dev

Relevant checks:

- Frontend/: npm run build runs both vue-tsc type checking and the Vite build.
  npm run type-check checks types; npm run build-only compiles without that check.
- Frontend/: npm run format:check is read-only. npm run lint includes --fix and
  can modify files; npm run format also rewrites files.
- Backend/: npm run build and npm run lint check compilation/linting.
- Backend/: npm run test and npm run test:e2e are configured through Vitest.
  The visible e2e test is a starter Hello World test, not domain coverage, and
  initializes AppModule/Prisma, so it requires database configuration.
- Frontend/: npm run test:unit runs Node tests for Persian numeric parsing,
  invoice validation, currency conversion, Persian calendar boundaries,
  print-page markup, and theme persistence/fallback. UI checks are still needed.
- Backend/: RUN_INVOICE_DB_TESTS=1 npm run test:e2e opts into invoice integration
  tests against the configured database. They create tagged fixtures and remove
  only those fixtures; auto-increment sequences may advance. In PowerShell set
  $env:RUN_INVOICE_DB_TESTS='1' before invoking the command.

These commands are derived from repository configuration. This document update
does not certify a clean install, database migration, deployment, or test run.

snapshots, stock transaction boundaries, price-history semantics, integer money,
and the Persian UI when making changes. Check actual behavior rather than
assuming that a UI label or a successful build proves the business workflow.

Known unfinished areas: dedicated aggregate dashboard APIs, reports, stock adjustment,
complete shadcn-vue migration, authentication/authorization, scalable list
pagination, and domain test coverage. These are context for future work, not
features this document claims to implement.
