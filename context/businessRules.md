# قواعد کسب‌وکار و مدل داده

آخرین تطبیق قواعد فاکتور: 2026-11-01. هدف محصول و معماری در [aboutProject.txt](aboutProject.txt) است.
این قواعد را پیش از تغییر قیمت، موجودی، فاکتور یا ساختار دیتابیس بخوانید.

## کالا و دسته‌بندی

- مغازه به کد کالا نیاز ندارد؛ `sku` از مدل، DTO، API و رابط حذف شده است.
  شناسه داخلی عددی `Product.id` برای روابط و عملیات همچنان لازم است.
- نام کالا در کل کالاها، حتی کالاهای غیرفعال و دسته‌های متفاوت، یکتا است.
  سرویس نام را `trim` می‌کند و نام خالی را رد می‌کند؛ `Product.name @unique`
  رقابت همزمان ثبت‌ها را نیز پوشش می‌دهد. خطای تکرار به HTTP 409 و پیام فارسی تبدیل می‌شود.
- یکتایی فعلی، روی مقدار نام در PostgreSQL است؛ یکسان‌سازی حروف فارسی/عربی،
  فاصله داخلی یا مقایسه بدون حساسیت به حروف لاتین پیاده‌سازی نشده است.
- کالا دقیقاً یک دسته معتبر و واحد شمارش دارد. نام دسته نیز یکتا است.
- موجودی اولیه صفر است. DTO ساخت/ویرایش کالا اجازه ویرایش مستقیم `stock` نمی‌دهد.
- تعداد و موجودی عدد صحیح‌اند؛ مقدار کسری فعلاً مدل نشده است.
- کمبود موجودی یعنی `stock <= minStock`؛ وضعیت فعال را نیز در مصرف‌کننده بررسی کنید.
- حذف دسته دارای کالا مجاز نیست. حذف کالای دارای تاریخچه قیمت به غیرفعال‌سازی
  تبدیل می‌شود؛ در غیر این صورت، روابط محدودکننده دیگر هم ممکن است حذف را رد کنند.

## پول و قیمت

| محل | واحد ذخیره/ورودی |
| --- | --- |
| قیمت خرید و فروش کالا | عدد صحیح تومان |
| ورود خرید و قیمت اختیاری مرجوعی | عدد صحیح تومان |
| تمام فرم‌های برنامه و فاکتور جدید/اقلام/گردش فروش | تومان؛ رابط `currency = TOMAN` می‌فرستد |
| داده قدیمی فاکتور/گردش | `IRR` یا `TOMAN`؛ تبدیل براساس currency |
| پیش‌نمایش و چاپ فاکتور | ریال؛ تبدیل یک‌باره در InvoicePaper |

- هنگام افزودن کالا به فاکتور، همان قیمت فروش تومانی استفاده می‌شود؛ ورودی قیمت،
  تخفیف، پرداخت، بیعانه، حساب‌های باز و نهایی‌سازی همه تومان‌اند. بایگانی و گردش
  نیز تومان نمایش می‌دهند. `invoiceInTomans` داده قدیمی را برای فرم تبدیل می‌کند؛
  `invoiceInRials` فقط در InvoicePaper برای پیش‌نمایش و چاپ استفاده می‌شود.
- فاکتور جدید با مبالغ صحیح تومانی در TOMAN ذخیره می‌شود. برای حفظ مبلغ قدیمی
  ریالیِ نامضرب ۱۰، فرم تا یک رقم اعشار تومان را می‌پذیرد؛ در این حالت سند در
  IRR صحیح ذخیره می‌شود تا گرد نشود. تبدیل‌ها در سرور با Decimal انجام می‌شوند.
- DTOهای فاکتور/پرداخت/نهایی‌سازی currency دارند؛ رابط TOMAN می‌فرستد. حذف این
  فیلد برای سازگاری با کلاینت قدیمی همچنان IRR است. خروجی API currency اصلی را
  دارد؛ پیش‌نمایش محاسبه سرور ریالی است و قبل از ورود به فرم به تومان تبدیل می‌شود.
- جدول گردش، قیمت واحد ریالی را برای نمایش هماهنگ با انبار بر ۱۰ تقسیم می‌کند.
- از اعشار شناور برای محاسبات مالی دامنه استفاده نکنید؛ حدود عدد صحیح دیتابیس
  و ضرب تعداد × قیمت و مجموع فاکتور را هنگام اعتبارسنجی حفظ کنید.
- تغییر قیمت کالا از مسیرهای ویرایش/قیمت در تراکنش، تاریخچه و audit ایجاد می‌کند.
- تغییر گروهی روی کالاهای فعال و دسته انتخابی اعمال می‌شود؛ preview فقط خواندنی است.
  `PERCENTAGE` یعنی `round(oldPrice * (1 + value / 100))`؛
  `FIXED` یعنی جایگزینی با قیمت تعیین‌شده، نه افزایش به مقدار ثابت.
- ورودی‌های مبلغ از `MoneyInput` و `lib/moneyInput.ts` و قالب‌بندی/پارسرهای
  موجود استفاده کنند تا ارقام فارسی، عربی و لاتین و جداکننده‌ها درست بمانند.

## ورود خرید و مرجوعی فروش

- نقطه ورود رابط، آیکون‌های خرید و مرجوعی در ردیف هر کالا در `ProductsView` است.
  `ProductStockDialog` به همان کالا متصل است؛ صفحه مستقل ورود وجود ندارد.
- `PURCHASE` و `RETURN` هر دو موجودی را افزایش می‌دهند و گردش ثبت می‌کنند.
- `RETURN` در پیاده‌سازی فعلی، **مرجوعی فروش مشتری** است؛ برگشت خرید به تأمین‌کننده نیست.
- مرجوعی به فاکتور فروش نیاز دارد. تعداد مجاز، تعداد فروخته‌شده همان کالا
  روی همان فاکتور منهای تعداد قبلاً مرجوع‌شده است. سرور این محدودیت را اعمال می‌کند.
- رابط مرجوعی فقط فاکتورهای شامل کالای انتخابی را از ۵۰۰ فاکتور اخیر نشان می‌دهد.
- `unitPrice` اختیاری، قیمت خرید کالا را تغییر می‌دهد؛ تغییر آن تاریخچه قیمت می‌سازد.
  عملیات ورود، `STOCK_RECEIVED` را نیز در audit ثبت می‌کند.
- `ADJUSTMENT` در enum و DTO هست ولی سرویس آن را رد می‌کند.
- گردش `SALE` از ثبت فاکتور ساخته می‌شود، نه از فرم ورود.
- تعداد گردش مثبت ذخیره می‌شود؛ نوع گردش اثر افزایشی یا کاهشی را مشخص می‌کند.

## فاکتور و مشتری

- رابط فعلی انتخاب مشتری ذخیره‌شده را می‌خواهد؛ قرارداد API از رابط گسترده‌تر است
  و فیلدهای snapshot مشتری و `customerId` اختیاری را نیز پشتیبانی می‌کند.
- draft در حافظه مرورگر است. هشدار خروج درون برنامه وجود دارد ولی reload آن را حفظ نمی‌کند.
- نوع فروش `saleType` دو مقدار `REGULAR` (عادی) و `CREDIT` (نسیه) دارد؛
  فاکتورهای قبلی عادی باقی می‌مانند، حتی اگر settlement آن‌ها INSTALLMENT باشد.
- هر دو نوع حداقل یک قلم کالای فعال و تعداد صحیح مثبت می‌خواهند. در فروش عادی،
  قیمت غیرمنفی با حداکثر یک اعشار تومان الزامی است و می‌تواند با قیمت فروش فعلی کالا متفاوت باشد.
- در فروش نسیه قیمت واحد و جمع اقلام و قیمت گردش فروش `null` هستند؛ API قیمت
  و تخفیف نسیه را رد می‌کند. subtotal/total/discount فاکتور در دیتابیس صفرند،
  ولی رابط و چاپ مبلغ نهایی و مانده را نامشخص می‌دانند، نه تسویه‌شده.
- ذخیره فاکتور، snapshot اقلام، کاهش موجودی و ساخت گردش فروش، اتمیک است؛
  کسری موجودی یا خطا نباید فاکتور یا موجودی نیمه‌ثبت‌شده باقی بگذارد.
- `subtotal = sum(quantity * unitPrice)` و `total = subtotal - discount`.
  این محاسبه برای فروش عادی است؛ تخفیف مقدار ثابت و `paidAmount` بین صفر و total است.
- مبلغ پرداختی در نسیه بیعانه است و به جمع صفر فاکتور محدود نمی‌شود. سقف مبالغ
  فاکتور جدید و بیعانه ۱۰ میلیارد تومان (معادل ۱۰۰ میلیارد ریال) است. رابط فروش عادی پرداخت را از صفر شروع
  می‌کند و دکمه پرداخت کامل دارد.
- فروش دو نوع کلی دارد: `saleType = REGULAR` (عادی) و `CREDIT` (نسیه).
  فروش عادی دو روش پرداخت `settlement = CASH` (نقدی) و `INSTALLMENT` (اقساطی) دارد؛
  هر دو قیمت‌دارند. اقساطی با نسیه متفاوت است. در نسیه انتخاب نقدی/اقساطی نمایش
  داده نمی‌شود؛ مقدار INSTALLMENT قبلی صرفاً برای سازگاری ذخیره می‌شود.
- روش پرداخت هنگام ویرایش و چاپ فاکتور عادی حفظ می‌شود. روش پرداخت یا نوع فروش
  به‌تنهایی نشانه تسویه نیست؛ حساب باز عادی بر اساس مبلغ نهایی و پرداخت واقعی
  تعیین می‌شود. هیچ‌یک دفتر دریافت/پرداخت یا برنامه زمان‌بندی اقساط نیستند.
- حساب‌های باز شامل تمام نسیه‌ها و عادی‌های دارای `paidAmount < total` است؛
  فیلتر قبل از دریافت داده در دیتابیس اعمال می‌شود و محدودیت ۵۰۰ بایگانی ندارد.
- ثبت پرداخت از حساب‌های باز، فقط مبلغ پرداخت جدید را می‌گیرد و به مجموع قبلی
  در سرور اضافه می‌کند؛ روی موجودی یا اقلام اثر ندارد. فیلد فرم با صفر باز می‌شود
  و مقدار قبلی را نشان نمی‌دهد. دکمه تسویه کامل فقط مانده را وارد می‌کند.
- PATCH /invoices/:id/payment مقدار `paymentAmount` مثبت با currency می‌گیرد؛
  رابط مبلغ جدید را به تومان می‌فرستد؛
  جمع تراکنشی و increment اتمیک از گم‌شدن پرداخت قبلی جلوگیری می‌کنند. سقف مجموع
  پرداختی و مانده عادی در سرور بررسی می‌شوند؛ فاکتور عادی تسویه‌شده از فهرست
  خارج می‌شود. واحد ذخیره فاکتور قدیمی در سرور حفظ می‌شود.
- «نهایی‌کردن فاکتور» در حساب‌های باز، پیش‌نمایش محاسبه و ورودی پرداخت جدید دارد.
  نسیه با قیمت فروش فعلی کالا (تومان در فرم) قیمت‌گذاری می‌شود؛ عادی قیمت ثبت‌شده
  را حفظ می‌کند. فیلد تخفیف در نهایی‌سازی با مقدار قبلی (برای نسیه جدید صفر) پر
  می‌شود و قابل تغییر است. تخفیف با حداکثر یک اعشار تومان، بین صفر و جمع اقلام معتبر است؛ مبلغ نهایی
  و مانده براساس تخفیف انتخابی محاسبه و همان مقدار ذخیره می‌شود. ثبت اولیه نسیه
  تخفیف ندارد و API آن را رد می‌کند. پرداخت جدید جدا از مجموع پرداختی/بیعانه
  قبلی دریافت می‌شود.
- ثبت نهایی با تراکنش Serializable، قیمت اقلام نسیه و گردش‌های SALE را ثبت و
  نسیه را به REGULAR تبدیل می‌کند؛ تعداد، موجودی، شماره، تاریخ و snapshot طرفین
  تغییر نمی‌کنند. کالاهای غیرفعالِ قبلاً فروخته‌شده نیز قابل نهایی‌سازی‌اند.
- اگر پرداخت قبلی + پرداخت جدید >= مبلغ نهایی باشد، حساب از حساب‌های باز خارج
  می‌شود؛ در نسیه روش پرداخت CASH می‌شود. اگر مانده بماند، نسیه به عادی اقساطی
  تبدیل و در حساب‌های باز باقی می‌ماند. روش پرداخت عادی قبلی حفظ می‌شود.
- مبلغ کل با کسر پرداختی بازنویسی نمی‌شود؛ مانده = total - paidAmount است تا
  پرداخت‌ها دوباره کسر نشوند. فاکتور چاپی پرداختی/بیعانه و مانده را زیر اقلام دارد.
- پیش‌نمایش توکن وابسته به وضعیت فاکتور و قیمت‌های نسیه دارد. اگر پرداخت، اقلام
  یا قیمت روز تغییر کنند، ثبت با 409 رد می‌شود تا کاربر محاسبه جدید را ببیند؛
  تکرار درخواست دارای پرداخت، مبلغ را دوباره اضافه نمی‌کند.
- بیعانه قبلیِ بیشتر از قیمت روز حفظ و مازاد به‌عنوان بستانکاری در فاکتور نمایش
  داده می‌شود؛ پرداخت جدید بیشتر از مانده پذیرفته نمی‌شود. نهایی‌سازی فاکتور قدیمی
  قدیمی، مبالغ را براساس currency و ورودی تومانی بدون گردکردن حفظ می‌کند.
- ویرایش مستقیم و قیمت‌گذاری دستی نسیه نیز از مسیر ویرایش فاکتور در دسترس است.
- شماره فاکتور از id با حداقل سه رقم ساخته می‌شود. تاریخ صدور `issueDate`
  مستقل از `createdAt` و در دیتابیس date-only است؛ ورودی API به صورت ISO است.
- پیش‌فرض تاریخ رابط، امروز تهران و نمایش تقویم فارسی است.
- ویرایش فاکتور، اقلام و گردش‌های فروش را جایگزین و موجودی را در تراکنش
  Serializable تطبیق می‌دهد. فاکتور دارای مرجوعی قابل ویرایش نیست.
- نام/واحد کالا و اطلاعات مشتری/فروشگاه روی فاکتور snapshot هستند؛ تغییر داده
  زنده نباید تاریخچه فاکتور صادرشده را بازنویسی کند.
- حذف مشتری، ارتباط `customerId` را null می‌کند؛ snapshot مشتری باقی می‌ماند.
- مرجوعی موجودی را برمی‌گرداند ولی مبلغ فاکتور را عوض نمی‌کند و سند استرداد پول نمی‌سازد.
- چاپ با `InvoicePaper` و A5 افقی است. ظرفیت پایه ردیف‌های معمول: صفحه اول ۱۷،
  میانی ۲۰، آخر ۱۶ و تک‌صفحه‌ای ۱۳ است. ارتفاع واقعی متن می‌تواند ظرفیت را کاهش دهد.
  سربرگ تکرار می‌شود؛
  طرفین فقط صفحه اول و جمع/یادداشت/تسویه/شبا/امضا فقط صفحه آخر هستند.
  پیش‌نمایش draft موجودی را تغییر نمی‌دهد. چاپ اقدام صریح کاربر است؛ endpoint PDF نداریم.

## مدل‌های اصلی

منبع معتبر: `prisma/schema.prisma`.

| مدل | نقش |
| --- | --- |
| Category / Product | دسته، نام یکتای کالا، قیمت، واحد، موجودی و وضعیت |
| PriceHistory / AuditLog | سابقه قیمت و ثبت عملیات منتخب؛ دفتر مالی کامل نیستند |
| InventoryTransaction | گردش کالا و ارتباط احتمالی با فاکتور |
| Buyer | اطلاعات مشتری، کد ملی اختیاری یکتا و راه تماس |
| Invoice / InvoiceItem | سند فروش و snapshot اقلام و طرفین |
| StoreSettings | رکورد تنظیمات فروشگاه با id برابر ۱ |

روابط تاریخچه، audit، گردش و اقلام با کالا محدودکننده حذف هستند.
`changedById/changedByName` در تاریخچه، به معنی وجود User یا احراز هویت نیست.

## مسیر آینده حساب‌های دفتری

هدف، کمک به حساب‌های روزمره همین مغازه است. پیش از پیاده‌سازی، صاحب پروژه باید
تعریف اشخاص و مانده اولیه، دریافت و پرداخت، فروش نسیه، برگشت و تسویه، اصلاح
اسناد و گزارش مانده را مشخص کند. مدل فعلی برای این موارد قرارداد کامل ندارد.
از `paidAmount`، audit یا گردش انبار به‌تنهایی مانده حساب معتبر استنتاج نکنید.
توسعه آینده باید تاریخچه فاکتور و داده‌های موجود را حفظ کند و migration داشته باشد.
